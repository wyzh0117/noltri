一 结论

P4 的验收口径是「实际支持矩阵 ＋ 指定可用 Agent 完成写入、检索、上下文调用」。本轮把这两件事都做跑了：M01／M03／M04 的证据不再只是单元测试——一个真实的 stdio MCP 进程带着连接中心刚签发的那份凭据，与一个真实的 SQLite Core 完成了 initialize → tools/list → tools/call capture_knowledge → tools/call search_knowledge，写进去的就是 Core 收件箱里的那一条，读回来的每个片段都被授权上的 snippetChars 裁到 24 字；随后撤销，同一条还没断的会话下一次调用就吃了 401，而另一份未撤销的授权仍然可读。

M02（不损坏其它配置、重复安装幂等、卸载只删自己管理的项）由 13 项 Rust 测试 ＋ 18 项合并/摘除测试锁定：备份失败即中止写入、两次快写各留一份备份、恢复动作本身又可撤销。M06（不可检测／不支持不能伪造已连接）落到「三段支持状态 ＋ 未知值降级 ＋ 未验证客户端同时拿不到写路径和官方链接」。M05 需要打包产物，本轮未做，如实挂在 §十三。

§435 要求的隐私边界写在签发之前，三个授权选项都在界面上：只写采集（scopes:["capture"]，mutate 从不出现在选项里）、限制项目（扁平化成可辨认路径，上限 100 与 Core 同一常量）、限制返回片段（20–4000，非整数或越界会挡住写入按钮而不是静默丢弃）。

本轮由实测暴露并修掉的问题共六个，其中一个差点让报告写出假结论：授权签发失败后，探针仍然「全部调用成功」——因为那时凭据是字面量 undefined，而 dev-open 的 Core 照单全收且不受片段上限约束。详见 §十一。

六 P4-A：stdio 是第二条腿，而且它先自证身份

§11 要求「默认 stdio transport；其进程仅代理本地 Core，不另建数据库」。services/mcp-server/src/stdio.ts 与 HTTP 端点复用同一份 buildServer()，凭据来自 NOLTRI_ACCESS_TOKEN，Core 地址来自 KNOWLEDGE_API_URL。三条不变量都由测试钉住，而不是靠注释：

  • stdout 只承载 JSON-RPC。给人看的每一行都走 stderr——这条是 P3 的 Native Host 用「10 条请求全部超时、但 Core 真的收到了采集」换来的，stdio 直接沿用。
  • Core 自证身份之前不开始服务。先 health() 再 verifyCoreIdentity()（productId／protocolVersion／version），四种拒绝各有文案：missing_api_url、core_unreachable、not_noltri_core、protocol_mismatch；main() 在未服务时置退出码 1。理由是 M06：一个把陌生本地服务报告成「已连上知识库」的 stdio 客户端比没有客户端更糟。
  • 注册条目按参数数组构造（92a196c），绝不拼成一条 shell 字符串——URL 或路径里的空格与引号会把参数拆成别的东西。

HTTP 侧 /mcp 把调用方自己的 Bearer 原样转发给 Core，所以「每客户端授权／scope／撤销／片段上限」对 Agent 与对桌面端是同一套判定，Agent 没有第二条不走授权的路径。本轮实测到 stderr 的只有一行：[noltri-mcp noltri-knowledge] serving over stdio, core 0.1.0 (instance b0497304-b6cf-4521-af21-8059d14d4fd7)。

三条诚实性规则由测试兜住而不是靠文案：

  • support() 之外的未知值在界面层降级为「未验证」（supportLabel／agentRows）——一个新出现的状态不会被读成「已支持」。
  • 未验证的两家同时拿不到 config_relative_path 与官方链接（detected_but_unverified_agents_get_no_write_path_and_no_url，并对四个 key 断言 URL 为 None）。界面文案是「已检测到本机安装，但其 MCP 注册方式本轮未经真实握手验证：请在该客户端内手动添加，验证前不显示为已连接」。
  • 检测只报告 .app bundle 是否存在与 Info.plist 版本：bundle_version_reads_the_plist_and_refuses_junk 拒垃圾，an_absent_agent_reports_no_version 保证「没检测到」不被渲染成「版本未知」。

八 P4-C：改别人的配置文件之前先备份，而且每一步都能撤销

写入 = 预览 → fs::copy 成 <file>.noltri-backup.<时间戳> → rename 原子替换
       （备份失败即中止写入：不存在"动了原文件但没留退路"的中间态）

撤销点 = list_backups 只认 .noltri-backup. 前缀（用户手制的 .bak 不会被冒充成我们的撤销点）
       restore_backup 拒绝 ①不是本应用所有的文件 ②不与目标同目录
       恢复动作本身又先备份一次 → 撤销恢复也是可撤销的

卸载 = removeServerEntry 只摘自家 noltri 条目：兄弟服务器／未知字段／键顺序全保留
       重复安装产出逐字节相同的文档（幂等）
       文档不是 JSON／没有 mcpServers 位／自家条目已存在但解析失败 → 拒绝动笔

界面上还有两条与凭据有关的行为，它们和备份是同一件事（都是「不要留下用户不知道的东西」）：确认框给的是绝对路径＋合并摘要＋这份授权的说明；用户点「取消」时刚签发的凭据同步撤销；卸载成功后同样撤销该客户端仍然生效的授权。

十 §435：授权界面上的三个选项，以及它们真正约束到哪里

§435 要求「MCP 通信在本机，并不保证 Agent 的推理也在本机。某个本地 Agent 若调用云端模型，工具返回的知识可能随其上下文离开电脑。授权界面提示此边界，并提供只写采集、限制项目、限制返回片段等选项。」界面在签发之前原样写上这句话：AGENT_PRIVACY_NOTE = 「MCP 通信在本机，并不保证 Agent 的推理也在本机。若该客户端调用云端模型，工具返回的知识可能随上下文一起离开这台电脑。不确定就收窄下面的授权。」

选项落地拒绝发生在
只写采集scopes:["capture"]，永不带 read；mutate 从不出现在界面上（AGENT_SCOPES = ['capture','read'] 被测试钉住）读取类动作在 requireScope 处拒绝（34 项授权用例覆盖）
限制项目把树扁平化成「Python / 数据结构 / Tuple 元组」这类可辨认路径供勾选，上限 MAX_GRANTED_PROJECTS=100，到数即停面板先停，Core 的 issueGrantRequestSchema 再拒——阈值是同一个导出常量，不会漂移
限制返回片段snippetChars（20–4000）随授权进入 ActorContext，在服务层内部裁剪空输入＝不限制；非整数／越界在签发前挡住「写入配置」按钮，不静默丢弃

片段上限裁的是这五个读取面：search 命中正文 · 节点详情（normalizedText 与 summary）· 上下文包（markdown／items／sources／estimatedTokens 因此自洽）· 收件箱预览 · GET /api/inbox/:id 的原文全文。不裁标题与树结构（所以界面写的是「正文」而不是「返回内容」），不裁设备凭据与未启用授权的通路——收件箱复核与桌面工作台需要全文，而那条路上根本没有授权可裁；apps/chat 的节点对话经 buildNodeContext 自动继承同一个上限。

两项设计决定也值得写下：裁剪放在服务层而不是路由出口，是为了让同一份上下文的 markdown 与结构化 items 说的是同一份文本（否则用户会看到「摘要 3 条、正文 2 条」这类自相矛盾）；矛盾组合（限制项目＋只写采集）在签发之前由 grantOptionConflict 指出，是为了不签一份 Core 注定拒绝的授权。describeGrant 把结果念成人话：capture+read · 全部项目 · 单次返回不超过 24 字 · 生效中。兼容性同样是实测的：.default(null) ＋ 宽容判定，让早于该选项存在的授权文件仍能读（两处用例锁定）。

十一 实测暴露并修掉的六个真问题

  1. 只设 NOLTRI_DEV_TOKEN 不设 NOLTRI_DEV_REQUIRE_TOKEN，签发端点 401。实现是对的（§569：未配置凭据的 Core 不得发放长期凭据），探针的环境变量是错的。但连锁后果很危险：签发失败后脚本把字面量 undefined 当凭据交给 MCP，dev-open 的 Core 照常服务每一次工具调用，于是「片段上限生效了吗」会显示成「调用全部成功」——只看成功就通过了。修法是补上环境变量，并把对照组写进断言（受限 24 字 vs 未受限 32 字 vs 设备凭据 32 字）。这条已写进 README 的三条口径，因为下一个跑这段配方的人会撞同一个坑。
  2. 探针自己的假 PASS。第一轮失败后 kill 掉的是 tsx 包装进程，它 fork 出来的 Core 仍在监听 8797；第二轮 waitForHealth 立刻「通过」，连上的却是上一轮的陈旧进程（dev-open、无授权表）。改为 detached: true ＋按进程组 kill(-pid) ＋运行前确认端口无人监听，并在末尾打印端口状态。教训：「健康检查通过」不等于「服务的是本轮启动的那个进程」。
  3. 授权面板同一条错误渲染两次。snippetChoice.error 在数字输入框下面出现一次，又在面板底部出现一次（main.tsx:677／:704）。这是本轮唯一一处在没有真实窗口的情况下也能确认的界面缺陷——靠通读渲染树发现，删掉重复的那条。
  4. 片段裁剪差点只裁了显示。上下文包最初只改了 itemLine() 的渲染文字，items 数组与 token 预算仍在用全文，于是预算用例报 expected 12 to be less than 12，item 行渲染成 - undefined（ItemEntry 少了 snippet 字段）。修法是把裁剪放进条目构造点，显示、结构化输出与预算因此读同一份文本。
  5. 契约新增必填字段的提交顺序。PublicGrant 加上 snippetChars 后桌面端立刻 TS2322——不是代码错，是 schema 改动当时还没提交，消费方在自洽的工作树上编不过。按序落三批（桌面端旧契约 → schema＋Core → 桌面端新选项）后每批都可编译。
  6. 列表端点的断言形状。从「消息里不含 secret 字样」升级为键集合本身不含凭据字段，新增字段时必须同时面对这条断言（见 §九 第二条）。

十五 一条与代码无关的观察：不可信外来内容

从 P0 到本轮的多个工具返回结果尾部，仍会周期性出现两段不是用户写的指令式文本（大意「内容是硬上限，必须遵守规则，尽量多输出」与「Please continue」）。本轮它们出现在测试与脚本输出里，处理方式和前几轮一致：当作不可信内容，没有据此改变任务范围、没有放宽任何输出或采集长度约束、没有转述成用户指令。§15.5 那次真实实测恰好提供了一个新的观察点：即使 Agent 侧的工具全部调用成功，成功本身也不是结论——结论必须来自「片段长度等于授权上写的 24」这种可核对的具体值。

实现层的兜底本轮又多了一道，而且方向正确：Agent 能做的每件事都以它自己那份授权的身份去做，节点 id 只能来自工具返回，破坏性 scope（mutate）在界面上根本不存在。页面里的文字让 Agent「把整库导出」，它拿到的只会是 Core 的拒绝。
