一 结论

P6 的验收口径来自开发文档 §19 的 R04／R05／R07 三行与契约 §5（六类偏移、Map 与 Context Pack 的口径，P5 时已冻结存档）。本轮把这三行从契约实现成代码：drift.ts 的六类规则（纯函数，不调模型）＋ 领域包装（并发取快照 → 跑规则 → 按五元组去重落库 → 汇总 summary），map.ts / context-pack.ts 两份纯装配，五条新端点（drift-check / drift-findings 列表 / drift-findings 状态更新 / map / context-pack），研究端点总数到 38 条且架构门禁把条数钉死；客户端侧 api-client 补齐五个类型化方法（33 → 38 个调用，45 行 WIRE 表），shared 补三张词表，桌面新增偏移检查／研究地图／上下文包三个视图（六 → 九视图）。R04、R05、R07 三行全部转绿。

两件最容易做假的规则被测试钉死。其一，无 AI 诚实（R05）：drift.ts 只 import schema 类型与 shared 的 tokenize，没有 IO、没有时钟、不生成 id、不调模型——落库与盖戳只发生在领域包装里，纯函数用例断言「同一快照产出同一份草稿」；契约 §5 继续作为规则存档。其二，去重口径：重跑不是又建一遍，而是按 (driftType, sourceEntityId, targetEntityId) 把草稿并入仍处于 open 的既有条目，返回集合同一、id 不变（demo 用例两次运行逐 id 相等）；人工处理（确认／解决）只改 finding 状态，判断永远在规则侧。

本轮还补齐了 P5 报告 §十三 承诺、却差点落空的 R06 后半句：「后续检查绑定新基线」。审计发现第一版实现（以及被归档的参考构建）只拿草稿行做对照；修复后 runDriftCheck 多取一路 findCharterBaseline，规则对照的最新已批准基线快照、无基线时回退草稿行——只改草稿、不批准，偏移不会消失。新用例把两半都钉住：改草稿不批准 → 发现照旧；批准 v2 之后再跑 → 偏移按新基线消失。

诚实边界：五条 P6 端点对 grant-scoped 的 Agent 客户端按设计不可达（契约 §4：研究文本尚未被 §435 的片段上限覆盖，一条都不开）；桌面三个新视图只有渲染级测试（renderToStaticMarkup），本轮没有可截的真实窗口操作；R03 仍只有归档路径（没有删除／合并）；21 项 PG 用例照旧跳过、不计通过。详见 §十。

六 六类偏移规则与去重（契约 §5 的实现）

drift.ts 是纯函数：读一份快照，返回 finding 草稿。落库、盖戳（id／createdAt／status）与去重都发生在领域包装 runDriftCheck 里。六类规则的触发与 severity 口径：

规则触发条件（确定性）severity建议动作（节选）
evidence_drift论点没有任何 supports／partially_supports 关系（反证与限定不算支撑）confirmed → critical；其余 warning补充 Evidence、弱化 Claim 或改为 Future Research
causality_drift强因果表述（cause／lead to／导致／影响／决定……）且支持证据为空或以非统计类型为主（expert_judgement／note／interview／document／external_source／other）boundary 空 → critical；含弱化词（suggest／相关／may……）→ info；否则 warning弱化为相关性表述或在 boundary 中限定推断程度
rq_drift仅当带 manuscriptText：正文中像研究问题的句子（问号／RQn／whether-how-what-why／「研究问题」）与 Charter 与已登记 RQ 归一化匹配失败warning登记到 Charter 或 RQ，或修订正文表述
contribution_driftcontribution 类论点与 Core Contribution 的去停用词 token 重合率 < 0.2；另有正文贡献句扫描（contribut／贡献）Core Contribution 空 → critical；否则 warning对齐核心贡献表述，或改写 Claim／更新 Charter
method_driftmethod 类 ResearchChange 晚于章程更新时间warning同步更新 Charter 的 Research Method、RQ 与 Boundary
journal_driftjournal 类变更，或（已选目标期刊时）contribution／scope 变更晚于章程warning同步更新 Target Journal、Core Contribution 与 Boundary
去重与返回口径（契约 §5）：去重键是 (driftType, sourceEntityId, targetEntityId)；重跑时草稿若命中一条仍处于 open 的既有 finding，就并入返回而不重复建档——结果集＝既有 open 条目＋本轮新建，summary 按返回集合统计。demo 用例两次运行逐 id 相等；只改草稿不批准基线，偏移不会消失（R06，§九）。已标为 acknowledged／resolved／dismissed 的条目不再占位：规则若仍命中，会重新开一条（判断在规则、状态在 finding；桌面只提供 确认→acknowledged、解决→resolved 两个动作）。

七 研究地图与上下文包（纯装配，排版归 UI）

研究地图 GET …/map

map.ts 把项目、章程要点（workingTitle／coreContribution／researchBoundary／claimBoundary／currentStage）与四层实体（questions → evidence → claims → sections）聚合成一份可画的图层：

  • 边集只保留七种关系 × 三种三元组：evidence→claim（supports／partially_supports／contradicts／qualifies／contextualizes）、claim→RQ（answers）、claim→section（appears_in）；决策与变更的边不进地图。
  • unsupportedClaimIds 与「有支撑」口径完全一致（只认 supports／partially_supports）——所以 evidence_drift 命中的论点在同一份地图上一定是无支撑的（demo：C-03 同时出现在两处）。
  • 每个 claim 带 supported 布尔；服务器不排版、不算坐标，只交图。

上下文包 GET …/context-pack

context-pack.ts 按契约顺序装配 12 个区块：PROJECT／Current Research Question／Core Contribution／Research Boundary／Claim Boundary／Current Method／Confirmed Claims／Key Evidence／Important Decisions／Recent Changes／Open Issues／Current Drift Warnings。markdown 与 blocks 由同一批字符串拼接（「同源」，两种表示永不互相矛盾）；Key Evidence 只取支撑 confirmed 论点的证据，决策与变更各取最近 5 条，警告只带 open 的 findings；generatedAt 由领域包装盖戳（纯装配不知道时间）。demo 断言：12 区块、block[0]＝PROJECT、block[11] 能读到 C-03 与 C-05 两条警告原文。

九 R06：检查绑定新基线（本轮补齐的缺口）

P5 交付了批准基线的前半句（append-only 版本、快照不可变、按名打复核标记），后半句「后续检查绑定新基线」被写进契约 §7、baselines.ts 注释与 P5 报告 §十三，约定由 P6 的 drift-check 读 findCharterBaseline 完成。审计时发现第一版实现（以及被归档的参考构建与归档契约）只拿章程草稿行做对照——承诺在文档里、行为还没到。修复（e52176f）很小，语义变化不小：

  • runDriftCheck 的并发快照从七路变八路，加上 repo.findCharterBaseline(projectId, userId)；
  • 规则对照的章程＝baseline?.charter ?? charterDraft——有基线时对照最新已批准基线的快照，无基线时（首次批准之前）回退草稿行；
  • 只改草稿、不批准，偏移不会消失：草稿编辑不移动参照系，只有批准一次修订才会。

区分两半的用例（research-drift.test.ts 第 29 项）：贡献论点与 v1 基线脱节 → 有偏移；把草稿改成与新论点一致（不批准）→ 偏移照旧（对照仍是 v1 快照）；把这条标注 dismissed、批准 v2 → 再跑，偏移按新基线消失。demo 与 restart 用例各自走上回退路径与「批准但未跑检查」路径，无回归。
