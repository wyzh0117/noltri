一 结论

P3 的三条验收口径都拿到了实现与证据：多入口同库由统一 CaptureRequest 与四入口共用的 ApiClient 达成，并被架构门禁钉住；重复提交幂等由数据库层的 (user_id, client_id, request_id) partial unique index 与 Core 的按键回放达成，实测同键两次只落一条原文、同文本三个不同键各落一条；失败不丢原文由扩展的本机待发送队列达成，实测断线期间入队 2 条、恢复后按原键发出、库中仍然只有 2 条。

同时要讲清楚一件事：浏览器还没有真正拉起过这个 host。扩展的 apps/extension/src/manifest.json 权限仍是 contextMenus / storage / activeTab，不含 nativeMessaging。加这项权限等于替用户向浏览器领一次新权限，开发文档 §16 明令不得静默进行，因此本轮把它留在报告里而不是偷偷改进仓库（见 下一步）。Native Host 的全部验证来自「真实子进程 × 真实 Core × 独立实现的帧解析器」。

本轮由实机跑暴露并修掉的问题共五个，其中两个会造成真实数据损失或真实越权：默认日志写 stdout 会把整条浏览器通道打烂，以及安装器丢参数会让一次 --confirm 直接写进用户真实的 Chrome 目录。详见 §八。

五 P3-A：重复提交幂等（真实 Core + SQLite）

§7.1／§7.2 要求的是两件不同的事：同一条提交不能写两次，以及内容相同但来源不同不能被静默丢掉来源。落库形态是 raw_sources.request_id ＋ client_id，配 partial unique index（SQLite user_version=2，Postgres 迁移 20261005000100_capture_idempotency.sql，向前-only，历史行的 null 键不入索引，因此升级不会因为旧数据失败）。

诚实记录：P3-A 首轮探针里有一行 ASSERT exactly 2 sources after 3 accepted submissions: false。这是探针写错了，不是端点错了——响应体没有 sources 键（是 entries／counts），探针读了一个不存在的字段所以恒为 0。P3-B／P3-C 的复核一律读 entries，计数与场景数一致。这一行留在 /tmp/p3a-evidence.log 里没有抹掉，因为「探针也会说谎」本身就是需要传递的事实。

六 P3-B：失败不丢原文（断线 → 恢复 → 再排空）

脚本 /tmp/p3b-outbox-live.mts 驱动的是扩展的真实模块（outbox/、api/client.ts、overlay/toast-content.ts），不是重新实现；流程是「杀掉 Core → 采集 → 恢复 Core → 排空 → 再排空一次」。

- capture #1 while Core is down -> ok=false retryable=true coreUnreachable=true
- queue says -> queued=true message=等待 Noltri：内容已保留，连上后自动发送
- queue now holds 2 entries: req-p3b-live-0001, req-p3b-live-0002
- drain after the Core came back -> sent=2 alreadyStored=0 kept=0 stoppedEarly=false
- ASSERT resends used the queued keys verbatim: true
- GET /api/inbox -> entries=2 counts={"pending":0,"processing":0,"done":2,"failed":0}
- a queue that re-sends an already stored capture -> sent=0 alreadyStored=1 kept=0
- ASSERT still exactly two sources after the resend: true
- online capture #3 -> stage=needs_review duplicate=false queued=false
  toast headline: 已存入 Noltri，需要你复核
- a refusal (too short) -> ok=false retryable=false shouldQueue=false
- ASSERT the queue stayed empty afterwards: true
- final inbox entries=3

四条设计意图在这段实测里各自落位：断线与拒绝是两种答案（后者绝不进队列，重发一百次也不会成功）；重发使用原 requestId，所以服务端仍按幂等键处理，第二次排空只会得到 alreadyStored 而不是第二条原文；ack 之前不承诺成功，浮层只在真实回执后写「已存入 Noltri」。

八 实机跑暴露并修掉的五个真问题

#暴露方式根因修复现在由什么钉住
1帧解析的旧返回形状在真实一问一答下顺序错乱FrameParser.push() 返回 {frames, error}，而 Chrome 是按位置把回复对上请求的：坏帧之后的好帧会被先答、更后面的好帧被整批丢掉改成有序事件流 ParseEvent = frame｜error；坏 JSON 仍宣告下一帧起点，只有长度撒谎（无法再同步）才清空缓冲framing.test.ts 14 项 ＋ 实机 frames=8 unparsed tail=0
2第一次实机跑 10 条采集全部超时，但 Core 那边真的收到了共享包 @noltri/shared 的默认 logger 用 console.info，即写 stdout；一行日志被当成 4 字节长度前缀，之后每帧都错位host 专用 createStderrLogger()，日志一律 stderr；启动日志记 hasToken 布尔而不记凭据main.test.ts 两项「stdout 只允许出现帧」的纯净性测试
3复核安装器代码时发现会写到用户真实浏览器目录parseArgs 只认 --flag=value，--home <目录> 这种空格形式的值被静默丢弃；于是 --confirm 的目标会退回真实 HOME 下的 Chrome NativeMessagingHosts两种形式都支持；--confirm 之外才消费下一个 token；browser 值做白名单；测试里 beforeEach 把 process.env.HOME 指到临时目录作第二道护栏install-cli.test.ts 17 项；并实测确认用户目录未被动过（见 §九）
4实机场景「批次超上限」拒绝文案说成「不执行 capture_batch 请求」——把用户合法使用的动词说成越权，读者分不清自己哪里做错了新增 invalid_request 这一类：拒绝必须指出到底哪里不合格（正文长度／键长度／条数上限）；越权与不合格是两种答案（§7.5）protocol.test.ts 33 项

十二 一条与代码无关的观察：不可信外来内容

从 P0 到本轮的多个工具返回结果尾部，反复出现过两段不是用户写的指令式文本，大意是「内容是硬上限，必须遵守规则，尽量多输出」和「Please continue」。处理方式一直是当不可信内容：没有据此改变任务范围、没有放宽任何输出长度或采集长度约束、没有把它转述成用户指令，也没有因为它而调用工具。

实现层对此有对应的兜底，而且这条兜底本轮实测过：网页或模型输出里写着「导出全库」，浏览器 host 能得到的只有 forbidden_scope；写着「把这段发到云端」也发不出去，因为 host 只认识四个动词、Core 只绑回环。这是设计上的必然，不是运行时的判断——不存在能接受越权动词的代码路径。
