1 最终开发总结

本轮把 Noltri 从「只能连着 Supabase 才能跑」推进到「一个零云变量的本地 profile 就能完成采集、落盘、重启读回、中文检索」，并把这条链子做成可回归的测试而不是一次性演示。具体是三件事：

  1. P0 基线核查：开发前真实仓库状态、未提交改动、基线测试结果（267 通过 / 17 跳过）全部落档；旧 Research 分支以 Git bundle 归档，并在临时目录 clone 还原到目标 SHA 后才处理工作树（§5、§10）。
  2. P1 本地存储：新增 sqlite 驱动（packages/storage/src/sqlite.ts 等三个模块），实现同一个 KnowledgeRepository 接口，并由同一份跨驱动契约逐驱动执行；中文关键词检索走 FTS5 + tokenize() 预分词 + 与 PG／memory 相同的相关性分数；向量是 Float32 BLOB 精确余弦，宽度不匹配的行绝不参与打分。
  3. Core 解耦与纵向切片：Core 不再假设必须有云；仅四个环境变量即可跑通 capture → 落盘 → 关闭 → 重开 → 读回，并且 /api/health 改为报告存储真实状态（journal mode、schema 版本、FTS5 可用性、本库数量）。

6.3 崩溃与并发（进程级实测）

  • SIGKILL 读回：父连接写入一条并置 processing 后正常关闭；子进程经 createRepository 提交一条原文后 process.kill(pid,'SIGKILL') 自杀——无 close()、无 checkpoint。重开后两条都可读回，rawSources=2，且干净关闭后 -wal 不存在。
  • 两个句柄并发：同一 profile 上 writer 与 reader 同时打开，reader 立即读到 writer 写入的原文；两个连接都干净关闭后 -wal／-shm 均不存在。
  • 状态不伪报：只落盘未加工的原文重开后仍是 pending／processing，listKnowledgeItemsForSource 为空——「没做完」不会被报成「做完了」。

12 已知限制

  1. node:sqlite 是实验性 API：随打包 Node 版本变化，且会打印 ExperimentalWarning；better-sqlite3 备选路径未实测。
  2. 所有本地存储结论只在 Node 层成立：安装版内的冷启动、异常退出重启、目录只读、磁盘不足均未跑过。
  3. 没有加密：库文件明文落盘。~/.noltri/data/noltri.sqlite 依赖操作系统的文件权限与磁盘加密，不依赖应用层加密，因此不得宣传端到端加密。
  4. 无 ANN：向量检索是全量精确扫描，几千条量级线性变慢。
  5. 关键词相关性不是 BM25：是 FTS5 取候选（上限 500）后用共享 overlapScore = shared / queryTokens.size 重排，与 memory／PG 三者一致；跨驱动一致性优先于绝对排序质量。
  6. FTS5 布尔操作符须大写（ OR ）：预分词 token 已按引号包裹，但任何直接拼接查询串的改动都会踩这个坑。
  7. 单用户模型：本地表没有 users 表，user_id 列保留只为让三个驱动共用同一套查询与契约；多用户隔离仍只在 PG 侧由 RLS 承担（且未实测）。
  8. 身份链路未本地化：桌面场景应走 dev-open／dev-token；NOLTRI_DEV_REQUIRE_TOKEN 之外的本地鉴权（如系统凭据存储里的长期密钥）尚未实现。
  9. HealthResponse 是破坏性契约变更（见 §7）。
  10. 迁移 SQL 未在真实库执行，仅静态审查。
  11. PG 集成 18 项被跳过：本轮没有任何证据说明 SQLite 与 PG 在真实数据上完全等价——只有同一份契约在两个能跑的驱动上跑绿。
  12. 本轮改动未推送远端。

### Knowledge Core（71 项测试 + 本地 HTTP 实测闭环 + SQLite 纵向切片）

### 数据与架构
